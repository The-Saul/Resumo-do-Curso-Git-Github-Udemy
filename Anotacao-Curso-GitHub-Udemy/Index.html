Git e GitHub

O que é Git?


O Git é um sistema de controle de versão distribuído utilizado para registrar e gerenciar alterações em arquivos ao longo do tempo, especialmente em projetos de software. Ele permite que desenvolvedores acompanhem o histórico de modificações feitas em um projeto, retornem a versões anteriores quando necessário e trabalhem de forma organizada mesmo quando várias pessoas estão modificando os mesmos arquivos.

O Git funciona registrando snapshots do estado do projeto em momentos específicos, chamados de commits, que ficam armazenados no repositório. Cada commit representa uma versão do projeto e contém informações como as alterações realizadas, o autor da modificação, a data e uma mensagem descritiva.

Por ser um sistema distribuído, cada desenvolvedor possui uma cópia completa do repositório em sua própria máquina, incluindo todo o histórico de commits, o que permite trabalhar localmente sem depender constantemente de um servidor central.



Qual a diferença de Git e GitHub?


A diferença entre Git e GitHub está no papel que cada um desempenha. O Git é a ferramenta de controle de versão em si, ou seja, o sistema que gerencia o histórico de alterações do projeto e permite executar operações como git add, git commit, git push e git pull. Ele funciona diretamente no computador do desenvolvedor e pode ser utilizado completamente offline.

Já o GitHub é uma plataforma online de hospedagem de repositórios Git, que funciona como um servidor remoto onde os repositórios podem ser armazenados, compartilhados e acessados por outras pessoas.

Em outras palavras, o Git é a tecnologia que faz o controle de versões, enquanto o GitHub é um serviço na internet que permite armazenar repositórios Git, colaborar com outros desenvolvedores, gerenciar projetos e facilitar o trabalho em equipe.

WorkFlow do Git

Criando Repositório:

Primeiro criamos um repositório Git executando o comando git init dentro de um diretório do sistema operacional. A partir desse momento, aquele diretório passa a ser um repositório Git, pois o Git cria internamente a pasta oculta .git, onde ficam armazenados o histórico de versões, commits, branches e demais informações de controle de versão. Dentro desse repositório existe o Working Directory, que é o diretório de trabalho onde os arquivos do projeto realmente ficam e onde o programador realiza alterações, cria novos arquivos, modifica códigos ou remove conteúdos. Quando um arquivo é criado ou alterado no Working Directory, o Git detecta essas mudanças, mas elas ainda não fazem parte do histórico do projeto.

Stagin Area

Para preparar essas alterações para serem registradas no histórico do Git, utilizamos o comando git add, que envia os arquivos modificados para a Staging Area. A Staging Area é uma área intermediária onde ficam armazenadas temporariamente as alterações que serão incluídas no próximo commit. Essa área funciona como uma espécie de “área de preparação”, permitindo que o programador escolha exatamente quais modificações deseja registrar no histórico naquele momento. Caso um arquivo tenha sido adicionado à Staging Area por engano, é possível removê-lo dessa área utilizando o comando git restore --staged <arquivo> ou, em alguns casos, git reset <arquivo>, fazendo com que ele volte apenas ao estado de modificado no Working Directory.

Depois que as alterações desejadas estão na Staging Area, utilizamos o comando git commit para registrar essas mudanças no repositório local. O commit pode ser entendido como um snapshot do projeto naquele momento, isto é, uma espécie de “foto” do estado atual dos arquivos preparados na Staging Area. Cada commit gera um registro permanente no histórico do Git, contendo as alterações realizadas, a mensagem descritiva do commit, o autor da modificação e um identificador único (hash) que permite localizar aquela versão específica do projeto no tempo.

Commit, Push, Pull e Repositório (Local e Remoto)

Esses commits são armazenados inicialmente no Local Repository, que é o repositório Git presente na própria máquina do desenvolvedor. Caso o projeto utilize um repositório remoto, como um servidor ou uma plataforma de hospedagem de código, os commits podem ser enviados para esse servidor utilizando o comando git push. O git push envia os commits do repositório local para o Remote Repository, permitindo que outras pessoas tenham acesso às alterações realizadas no projeto. Por outro lado, quando existem atualizações no repositório remoto feitas por outros desenvolvedores, podemos utilizar o comando git pull para baixar essas alterações para o repositório local. O git pull basicamente realiza duas operações: primeiro ele busca as atualizações do servidor remoto e depois integra essas mudanças ao repositório local, mantendo o projeto sincronizado.

Dessa forma, o fluxo básico de trabalho no Git segue uma sequência lógica: o desenvolvedor modifica arquivos no Working Directory, utiliza git add para enviar as alterações para a Staging Area, registra essas alterações no histórico através de git commit, armazenando-as no Local Repository, e finalmente utiliza git push para enviar esses commits para o Remote Repository. Quando novas alterações estão disponíveis no servidor remoto, o desenvolvedor pode utilizar git pull para trazê-las para sua máquina, garantindo que todos estejam trabalhando sobre a versão mais atual do projeto.

Os Comandos “git rm" e “git add" São Opostos?

O Git não é diretamente responsável por criar ou apagar arquivos, pois essa é uma função do sistema operacional ou das ferramentas utilizadas pelo desenvolvedor. Arquivos e pastas podem ser criados com comandos do sistema como mkdir (criar pasta), touch (criar arquivo) ou diretamente por meio de um editor de código. O papel do Git é rastrear e registrar as mudanças que acontecem nesses arquivos dentro do projeto, mantendo um histórico das versões ao longo do tempo.

Quando um arquivo novo é criado no Working Directory, ele aparece no Git como Untracked (não rastreado). Para que o Git passe a versionar esse arquivo, usamos git add, que envia essa alteração para a Staging Area, ou seja, prepara essa mudança para o próximo commit. O comando git add não cria arquivos; ele apenas prepara alterações (criação, modificação ou remoção de arquivos) para serem registradas no histórico.

O comando git rm serve para remover um arquivo do projeto. Ele apaga o arquivo do Working Directory e já registra essa remoção na Staging Area, preparando-a para o próximo commit. Após executar git commit, essa remoção passa a fazer parte do histórico do repositório. Assim, ao utilizar git rm, o arquivo é removido do diretório do projeto e essa remoção é registrada para ser incluída no próximo commit.

Portanto, git add e git rm não são opostos diretos. O git add prepara alterações para o commit, enquanto o git rm remove um arquivo do projeto e registra essa remoção. De forma geral, o sistema operacional cria ou remove arquivos, e o Git registra essas mudanças no histórico do projeto.

Git Reset e Git Revert

Git Reset

O comando git reset serve para mover o ponteiro do histórico para um commit anterior, removendo da linha atual do histórico os commits mais recentes. Por exemplo, se o histórico for A → B → C → D e executarmos git reset --soft HEAD~1, o repositório volta para A → B → C, removendo o commit D do histórico atual, mas mantendo as alterações desse commit na Staging Area, prontas para um novo commit. Já com git reset --hard HEAD~1, o repositório também volta para A → B → C, porém as alterações do commit D são apagadas, e o Working Directory e a Staging Area voltam exatamente para o estado do commit C. Portanto, o git reset reescreve o histórico da branch, removendo commits da linha atual.

Existe também o git reset --mixed, que é o modo padrão do git reset quando nenhum modo é especificado. Nesse caso, o repositório também volta para o commit anterior, removendo o commit mais recente da linha atual do histórico, porém as alterações desse commit não são apagadas e não permanecem na Staging Area. Em vez disso, elas voltam para o Working Directory como modificações ainda não preparadas para commit.

Git Revert

O comando git revert funciona de forma diferente, pois não remove commits do histórico. Em vez disso, ele cria um novo commit que desfaz as alterações de um commit anterior. Por exemplo, se o histórico for A → B → C → D e executarmos git revert HEAD, o Git criará um novo commit E, resultando em A → B → C → D → E, onde E desfaz as alterações feitas em D. Dessa forma, todo o histórico original é preservado.

Branch

Uma Branch é uma linha de desenvolvimento independente dentro do mesmo projeto.

Ela permite que você trabalhe em novas funcionalidades, correções ou testes sem afetar o código principal.

A branch padrão geralmente se chama main (antigamente era master).

As Branches são usadas para:

  • desenvolver novas funcionalidades
  • corrigir bugs
  • testar ideias
  • trabalhar em equipe sem quebrar o projeto principal

O que acontece com os commits numa branch?

Quando você está em uma branch e faz commits, eles pertencem apenas a essa branch.

Exemplo:

A → B → C
        ↑
       main
        \
         D → E
             ↑
        login-feature

Agora existem duas linhas de desenvolvimento.

O que acontece quando terminamos o desenvolvimento na Branch secundária?

Juntamos as Branches secundárias com o main usando o Merge

Quando a funcionalidade estiver pronta, podemos juntar a branch com a main usando:

"git merge nome-da-branch" Isso integra o código da branch no projeto principal.

O merge é a mesma coisa que um commit?

Não exatamente. Merge não é simplesmente um commit comum, mas na maioria das vezes ele gera um tipo especial de commit chamado merge commit. A diferença é que um commit normal possui apenas um commit pai, enquanto um merge commit possui dois pais, pois ele une o histórico de duas branches diferentes. Porém, em alguns casos o Git faz um fast-forward, onde nenhum novo commit é criado; a branch apenas avança para o último commit da outra branch.

Códigos Git sobre a Branch:

  • git branch → listar branches
  • git branch -a → mostra todas (locais + remotas)
  • git branch nome → criar branch
  • git checkout nome → trocar de branch
  • git checkout -b nome → criar e trocar
  • git merge branch → juntar branch secundária com branch main

O que é GitHub?

O GitHub é uma plataforma online de hospedagem de repositórios Git. Ele permite que desenvolvedores armazenem seus projetos na internet, acompanhem o histórico de versões e colaborem com outras pessoas no mesmo código. Enquanto o Git é o sistema de controle de versão que funciona localmente no computador, o GitHub funciona como um repositório remoto, onde o projeto pode ser enviado (push) e de onde também pode ser baixado ou atualizado (pull ou clone).

Além de hospedar repositórios, o GitHub oferece várias ferramentas para colaboração e gerenciamento de projetos, como pull requests (para revisar e propor mudanças no código), issues (para registrar bugs, tarefas ou melhorias), controle de branches, histórico visual de commits e integração com ferramentas de automação e testes. Por isso, ele é muito utilizado tanto em projetos profissionais quanto em projetos open source, pois facilita o trabalho em equipe, o compartilhamento de código e o controle organizado das versões de um software.

Usabilidade do GitHub

O GitHub é uma plataforma muito intuitiva de usar. Criar um perfil, criar repositórios, pesquisar projetos ou navegar pelo código de outras pessoas acaba sendo algo bem natural depois de alguns minutos explorando o site. Por isso, muitas vezes nem vale a pena anotar passo a passo dessas coisas básicas, porque a interface guia bem o usuário.

Muita gente até diz que o GitHub funciona quase como uma rede social de desenvolvedores. Lá você pode visitar o perfil de outros programadores, ver os projetos que eles criaram, acompanhar atualizações e explorar os repositórios públicos. Essa parte é extremamente valiosa para aprendizado, porque dá para abrir um projeto e examinar o código linha por linha, entendendo como outras pessoas resolveram determinados problemas.

Quando um repositório é público, também é possível baixá-lo para o seu computador (clonar o projeto) e estudá-lo com calma. Assim você pode testar, modificar o código e aprender na unha mesmo, mexendo diretamente nos arquivos e vendo na prática como tudo funciona. Essa troca de conhecimento é uma das coisas que tornam o GitHub tão importante para quem está aprendendo ou trabalhando com programação.

Os Iniciantes confundem os comandos: Fork, Clone, Pull e Fetch.

Fork

Fork é uma funcionalidade do GitHub. Ele cria uma cópia de um repositório na sua própria conta.

Fluxo:

Repositório original → Fork → Repositório na sua conta

Isso é muito usado em projetos open source, porque você pode modificar o código sem alterar o projeto original. Depois, se quiser contribuir com melhorias, pode enviar um pull request.

Clone

Clone é um comando do Git usado para baixar um repositório remoto para o seu computador.

Comando:

git clone URL_DO_REPOSITORIO

Ele cria:

  • uma cópia completa do projeto
  • todo o histórico de commits
  • conexão com o repositório remoto

    Fluxo:

    GitHub → clone → seu computador

Fetch

Fetch baixa novos commits do repositório remoto, mas não altera seu código atual.

Comando:

git fetch

Ele apenas atualiza as referências do repositório remoto. Ou seja, o fluxo é:

remote repository → fetch → atualiza informações

Mas seu código continua igual até você fazer um merge ou pull.

Pull

Pull traz as atualizações do repositório remoto e já integra essas mudanças na sua branch local.

Comando:

git pull

Internamente ele faz:

git fetch + git merge

Fluxo:

remote repository → pull → atualiza sua branch

Remote Repository

Um Remote Repository é um repositório que está em um servidor, como no GitHub. O comando git remote add origin URL registra o endereço desse repositório remoto dentro do repositório local, permitindo enviar (push) ou baixar (pull) alterações. Diferente de git clone, que já cria a pasta, baixa os arquivos e configura o remote automaticamente.

Origin é apenas um nome (alias) dado a esse repositório remoto, permitindo usar comandos como git push origin main em vez de digitar a URL completa: "git push https://github.com/usuario/projeto.git main". Então, origin → https://github.com/usuario/projeto.git.

O comando git clone cria um repositório local a partir de um repositório remoto. Internamente ele cria a pasta do projeto, inicializa o Git, configura o remote origin, baixa o histórico de commits (fetch) e cria uma branch local baseada na branch remota. Esse processo poderia ser feito manualmente com git init, git remote add, git fetch e git checkout -b main origin/main.

Flags

Uma flag é uma opção usada em comandos de terminal para modificar ou complementar o comportamento de um programa. Em ferramentas de linha de comando, como o Git, as flags são escritas após o comando principal e geralmente começam com um hífen (-) ou dois hífens (--). Elas servem para indicar ao programa como a operação deve ser executada ou quais informações adicionais devem ser fornecidas.

-m / --message

message → mensagem do commit.

Serve para escrever a descrição do commit diretamente no comando. Por exemplo:

  • git commit -m = Adiciona página inicial
  • git commit --message = Adiciona página inicial

-a / --all

all → todos os arquivos modificados.

Adiciona automaticamente ao commit todos os arquivos modificados que já estão sendo rastreados pelo Git (não inclui arquivos novos). Por exemplo:

  • git commit -a -m "Corrige erro no cálculo"
  • git commit --all -m "Corrige erro no cálculo"

-f / --force

force → forçar operação.

Força uma ação mesmo que o Git detecte algum risco ou conflito. Por exemplo:

  • git push -f
  • git push --force

-d / --delete

delete → deletar.

Remove algo do repositório, geralmente usado para apagar branches. Por exemplo:

  • git branch -d minha-branch
  • git branch --delete minha-branch

-D

delete (forçado) → deletar à força.

Apaga uma branch mesmo que ela não tenha sido mergeada. Por exemplo:

  • git branch -D minha-branch

-b / --branch

branch → branch (ramificação).

Cria uma nova branch e já muda para ela. Por exemplo:

  • git checkout -b nova-feature
  • git switch --branch nova-feature

-v / --verbose

verbose → modo detalhado.

Mostra informações extras sobre o que está acontecendo. Por exemplo:

  • git remote -v
  • git status --verbose

-u / --set-upstream

upstream → conectar branch local com a branch remota.

Define para qual branch remota a branch local deve enviar e receber atualizações. Por exemplo:

  • git push -u origin main
  • git push --set-upstream origin main

Para Fixar:

- m → message (mensagem)
- a → all (todos)
- f → force (forçar)
- d → delete (deletar)
- b → branch (criar branch)
- v → verbose (detalhes)
- u → upstream (ligar ao remoto)

SourceTree & GitHub

Sobre SourceTree

O Sourcetree é uma interface gráfica (GUI) para o Git. Ele permite visualizar e executar operações do Git, como commits, branches, merges, push e pull, sem precisar usar comandos no terminal. A ferramenta mostra o histórico do projeto em forma de árvore, facilitando a visualização da estrutura de commits e ramificações.

Comparação com GitHub Desktop

O Sourcetree e o GitHub Desktop têm o mesmo objetivo: permitir que o desenvolvedor utilize o Git através de uma interface gráfica. A principal diferença é que o GitHub Desktop foi desenvolvido pelo próprio GitHub e possui integração direta com a plataforma, enquanto o Sourcetree foi desenvolvido pela Atlassian e historicamente é mais utilizado com o Bitbucket.

Sobre GitHub Desktop

O GitHub Desktop é uma ferramenta gráfica que facilita o uso do Git para desenvolvedores que preferem não utilizar o terminal. Ele permite clonar repositórios, criar commits, visualizar alterações, trabalhar com branches e sincronizar o projeto com o GitHub de forma simples e intuitiva. Por ser integrado diretamente ao GitHub, ele se tornou uma das ferramentas mais populares para gerenciamento de repositórios nessa plataforma.
